# 文档规范

目标：文档永远值得信任。读者默认文档是对的——所以错文档比没文档更糟，这份规范是防"文档腐坏"的机制集合，不是靠自觉的口号。

## 一、单一事实源（SSOT，第一原则）

**每个事实只在一个地方说一次，其他地方只链接，不复制。**

- 例子：去重规则只写在公开仓 `docs/sources/claude-code.md`，ADR 引用它而不是复述；令牌公式只写在 `docs/design/令牌系统.md`
- 发现自己在两处写同一件事：停下，选权威方，另一方改链接
- 评审时搜关键词检查：同一规则出现两个版本 = PR 打回

### 跨仓事实映射表（2026-08-03 新增）

双仓结构下 SSOT 最容易在**仓库边界**上失效：2026-08-03 的审查发现，三轮终审的"同步修订"清单只列了内部仓文档，公开仓的 `docs/设计原则.md` 不在其中——于是它停在换栈之前，仍写着已被推翻的 uPlot、漏了第五套主题、并与动效规格在"签名时刻有几个"上直接矛盾。而仓库策略规定"公共子集以公开仓为权威"，结果是**最权威的那份最旧**。

修法不是再校对一次，是建表：每个跨仓重复出现的概念登记权威方与镜像方，任何一方改动时按表核对另一方。

| 概念 | 权威方 | 镜像方（须同 PR 核对） |
|---|---|---|
| 视觉原则与禁止清单 | 公开仓 `docs/设计原则.md` | `docs/design/` 三份 |
| 令牌数值与派生算法 | `docs/design/令牌系统.md` | 公开仓 `docs/设计原则.md` 的色彩/字体/圆角段 |
| 动效参数与签名时刻数量 | `docs/design/动效规格.md` | 公开仓 `docs/设计原则.md` 动效段与个性预算段 |

## 二、文档分寿命（不同文档，不同新鲜度语义）

| 类型 | 例子 | 寿命规则 |
|---|---|---|
| **活文档** | sources spec、架构总览、数据库-schema、设计图纸 | 与代码同生共死：行为变更的 PR 必须同 PR 更新，否则 CI/review 不过 |
| **不可变文档** | ADR | 只追加不修改；被推翻 = 新 ADR + 旧文头部标 `superseded by NNNN`，旧文永留 |
| **档案** | research/、审查报告 | 冻结，标日期；事后发现错只在文末加勘误，不改写历史 |

## 三、时效事实必须打戳

凡会过期的断言，写的时候带上时间与版本：

- 坏：`Linux 桌面体验较差`
- 好：`Tauri 2 桌面端 Linux 依赖 webkit2gtk-4.1（2026-08-02 三轮终审定）：低于该版本安装期警告，透明窗口默认不透明——M5 首次三平台截图比对验证（风险登记 R6）`
- 竞品数据、上游版本、外部 API 行为一律打戳；审查报告已证明无戳事实会骗人
- **版本号必须区分"能力版本"与"接口版本"**（2026-08-03 增补）：`webkit2gtk-4.1` 是 API/ABI 版本号，同一 API 下引擎跨越多个大版本、CSS 能力差距显著——用它当能力下限是一处真实的精度错误（[ADR-0009](adr/0009-运行期基线.md) 已修）。写下限时问一句：这个数字表达的是"能不能链接"还是"能不能渲染"
- **外部工具的维护状态属会过期事实**：分发链路、构建工具这类不可逆依赖，选型时须记录核实日期与版本，并写明它不可用时的回退路径（[ADR-0013](adr/0013-分发信任链.md) 对 cargo-dist 即按此办）

## 四、同步进流程（不是提醒，是门禁）

- PR 模板自查项（已有）：「涉及数据源格式→sources 已更新」「涉及架构决策→ADR 已更新」「涉及文案→双语已同步」；**新增「涉及跨仓概念→按跨仓事实映射表核对镜像方」**
- Definition of Done 含文档同步（已有）
- 每个里程碑收尾：花 15 分钟过一遍活文档目录，确认无已知落后项

**CI 门禁（2026-08-03：把"计划中的检查"变成具体条目并给出触发时机）**：

| 检查 | 内容 | 状态 |
|---|---|---|
| 内部链接死链 | 扫全部相对链接与锚点 | 待建（M0.5） |
| **DDL 一致性** | 从 `docs/数据库-schema.md` 提取 SQL 块建库，与迁移代码建的库做 `sqlite_schema` diff，不一致即红 | **待建（M0.5 冻结物）**——原文写"代码存在后"，代码已存在且已经漂了一张表，这道门禁本身就是冻结门的一部分 |
| 禁词扫描 | `可能` / `大概` / `应该是` 出现在 spec 类文档且未跟"未验证 + 验证方式"标注即红 | 待建（M0.5） |
| 私有路径泄漏 | 公开仓侧拒绝任何路径含 `internal/` 的暂存文件（pre-commit + CI 双层，见[仓库策略](仓库策略.md)） | 待建（公开仓恢复时第一批） |

禁词扫描不是文字洁癖：`可能`标记的是**未完成的调查**。当前仓内至少四处违反了这条自定规则（风险登记 R6/R7、ADR-0004 边角坑），本轮已逐条改为"已定的判据 + 待验证项 + 验证时机"。

## 五、简洁性标准

- 一份文档回答一个问题；超过两屏先想能不能拆
- 表格优先于段落，spec 优先于散文；能写规则不写描述
- 删除是正当维护：过时的段落删掉（git 记得它），不留"曾经是这样"的考古层——历史交给档案类文档和 git
- 禁词：`可能`、`大概`、`应该是`——要么查证后写死，要么明确标注"未验证"+ 验证方式

## 六、正确性标准

- 每个非显然的论断给证据：链接、issue 号、实测数据（"本机 141,830 行实测"）
- 示例值可复现：DDL 能建表、公式能编码、fixture 能跑测试——文档越接近可执行，越难腐坏
- 拿不准的事实不许写进 spec 类文档；写进"未决问题"区，带验证路径

## 七、文档索引的新鲜度

- README 与 docs/架构总览.md 的文档索引在新增/删除文档的同 PR 更新
- 每份文档头部不需要"最后更新"字段——git log 就是新鲜度记录，手工维护的日期字段本身就是腐坏源
