### B. 暖黑面板系 + 边界双级
**公式**（`derive.rs`，仅 dark 分支改动，light 分支未动——v7 无浅色目标，改了也没有验收依据）：

```
canvas_l = 0.13                              （原 0.17）
raised_l = canvas_l + 0.035                  （原 canvas_l + 0.03）
overlay_l = canvas_l + 0.055                 （原 canvas_l + 0.07）
panel_c(l) = bg0.c × 0.4 × (l / canvas_l)     （原：三级统一用 bg0.c 原值，无衰减）
```

`0.4` 与三处 L 偏移是对 v7 四个目标点（canvas/panel/panel2 三色 + 一份边框 rgba）反推出的最简公式，不是逐点拟合——已在报告末尾的「独立复算」节验证其在另一套独立实现下的确定性。`panel_c` 以 `bg0.c`（种子自身背景色的彩度）为唯一输入相乘，`bg0.c == 0` 的主题（mono、以及 paper 的 light 变体——它的 `bgBase` 就是纯白）自动得到零偏置，不需要按主题名字判断。

边框：新增 `border.tint`（L 与 fg.primary 同档、C 固定 0.02、H 取种子背景色相，`bg0.c == 0` 时降为 0）取代原来直接复用 `fg.primary` 做 base；`border.hairline` alpha 从 dark 0.10 降到 0.08，新增 `border.faint`（dark 0.05 / light 0.08）对应 v7 的 `--bd`/`--bd2` 两级。light 侧的 `border.hairline` alpha（0.12）未动。

**范围裁决**（需要记录的取舍）：提案 §四色彩系统修订同时提到"其余=金""兜底=暖灰"两个类目，但任务 C 给的种子清单只有 6 个名字（含一个 `fallback`），没有单独的"其余/金"条目——本次只实现了这 6 个，`fallback` 对应"兜底暖灰"；"其余=金"（给 copilot 等未来 adapter 用）没有对应种子，留给以后新增来源时再接（ADR-0018 本来就是开放集合，这里不是缺口，是范围内没有第 7 个名字可用）。

### E. 地形令牌
**关键发现**：v7 参考实现里 `top[0]/left[0]/front[0]`（数组下标 0，对应"无活动"格）在渲染循环里被 `if(!v)continue` 直接跳过，从未真正画到屏幕上——这三个值是死代码，不是设计目标。真正被验证过的是 `top[1..4]`，而它们与 `heat[1..4]`（dark: 0.35/0.493/0.637/0.78）逐值相等（最大偏差 0.2%，`top[4]` 完全相等）。据此把 **地形 top 面直接定义为 heat 数组的别名**（不重新派生，`terrain_top = heat`），而不是重新拟合一条五档曲线——省掉了一次容易和 heat 产生细微数值分叉的重复实现。

left/front 面：把 top 面（已量化的 8-bit 值）反解回 OKLCH，L 与 C 同时乘一个固定比例（0.80 / 0.65，对 v7 参考色的实测比例是 L 比 0.77–0.85、C 比 0.72–0.92，取中点常数），H 不变，再走一次 gamut 映射——由于该操作只把点朝黑色原点收缩，理论上必然留在色域内（已用单测覆盖，未依赖这个论证本身）。任务书"侧面为 top 的固定 L 降档"读作"固定比例衰减"而非"固定加减值"——后者对 v7 数字拟合不上（残差随档位从 0.04 涨到 0.13），前者两个面都在 0.02 以内。

明度序 `top > left > front` 由构造保证（0.65 < 0.80 < 1），并在 5 个主题 × 2 模式上跑了直接断言（`terrain_faces_are_ordered_top_over_left_over_front`）。产物：`--tokly-terrain-{top,left,front}-{0..4}` 共 15 个变量/变体；"峰值辉光色"复用 `accent.solid`、"地台色"复用 `bg.raised`，均为既有令牌的语义别名，未新增重复数值。

### H. 字体三层解析
新增 `overrides.fontDisplay` / `overrides.fontBody` / `overrides.fontMono`（Tier 1 可选字段，数组形状与静态 `fontFamily` 令牌一致，复用了 `dtcg::font_family` 解析器）。**范围裁决**：任务书写"仅系统安装字体+内置 Geist/Maple"，但 `tokly-tokens` 是纯函数 crate、明确无 IO（crate 文档原话），没有查询宿主已装字体的路径；因此把"系统安装字体"落地为一个**封闭白名单**——两个内置字体族 + tokens.json 静态栈里已经背书过的 CJK 回退名 + 常见 CSS 通用关键字（`sans-serif`/`monospace`/`system-ui` 等），拒绝清单外的任何名字（含单测 `Comic Sans MS` 用例）。真正的"查询宿主已装字体"属于 `tokly theme install`（跑在用户机器上，能做 IO），ADR-0017 已经把它定位成安装期职责，本次不越界实现。另外要求每个覆盖数组至少保留一个 CJK 回退名（`PingFang SC`/`Microsoft YaHei UI`/`Noto Sans CJK SC`），验证过缺失时报错并指到具体路径。

CSS 产出：新增 `--tokly-font-display` / `--tokly-font-body`（默认等于现有 `--tokly-font-sans`，写进 `:root`），`--tokly-font-mono` 复用现有变量、不新增同名角色变量。三级回退全靠 CSS 层叠本身实现——`:root` 给默认值，主题的 `[data-theme=...]` 块只在种子真的带了覆盖时才输出对应变量，未来 `tokly theme install`/用户配置要再加一层覆盖，只需在层叠顺序更后的地方再写一次同名变量，引擎这边不用改。10 个官方主题都没有用到这三个字段（未触发任何覆盖分支），行为对现有产物零影响，只在种子将来携带覆盖时才会体现。
