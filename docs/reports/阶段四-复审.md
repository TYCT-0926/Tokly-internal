## 一、结论与放行条件

本 PR 的常规门禁全绿，但高危正确性不成立。复审构造出 JSONL 替换静默丢数、API 半发布、计价改写不可变历史、compact 幽灵聚合键、冻结会话新事件漏报、部分成本伪装成完整账目等反例；P5/P6 oracle 又与契约同错或覆盖不全，现有绿灯不能排除这些错误。

以下项目全部修复并把本文红色反例恢复为永久回归前，不得合并：

1. 修复 B 节三条摄取丢数/半发布路径，并完成 SQLite pending 的端到端闭环。
2. 按 ADR-0002 已明确的 same-hash 零触碰语义，同时修 SUT 与独立 oracle。
3. 让 reprice、compact、report 遵守 pruned/frozen 与部分成本契约。
4. 使所有 health 查询可见提交与 `data_version` 同代，或以新 ADR 明确另立健康版本。
5. 补全 P6 全证据码双向模型，交付可审计的 18 项突变清单与 mutant→killer 映射。
6. 用六源 `bench-3y` + criterion 重建性能机构，验证完整产出、冷/暖态与稳态体积。

## 四、A—H 逐项复审

### A. 批事务下的收敛

**判无洞：核心批事务原子性成立。** `Store::ingest_batch` 在一个事务里执行所有 observation fold、dirty 标记、水位线发布与条件式 `data_version` 递增。复审新增的回归故意给 `SqlitePosition` 水位线绑定 `JsonlOffset`，让错误发生在三次 fold 全部执行之后；错误返回后 projection、observation、dirty、version、水位线均与调用前一致。

```powershell
cargo test -p tokly-core --test convergence a_batch_whose_watermark_fails_after_folding_leaves_no_trace -- --exact --nocapture
cargo test -p tokly-core --test convergence -- --nocapture
```

结果：定向回归通过；convergence 8/8 通过。交换、乱序、重放、重建在批事务提交粒度与 `3e3f2cc` 下未见新增语义漂移。

**建议：限制纯 skip/坏行批的内存。** `PendingBatch::is_full` 只按 observations 计数；若整文件只有 skip 或坏行，watermark advances 可增长到 EOF。可按 watermark key 只保留最大 advance。这不是本轮数据错误的放行阻断项。

### B. 三类水位线的丢数点

#### B1. JSONL 同长替换静默丢数——必须修复

adapter 已计算 `change_stamp` 并最终写入 `watermarks.file_id`，但真正做代际判断时调用 `resolve_jsonl_stream(&key, None, header_hash, size)`，没有传入刚算出的 file identity。构造：

1. 首次摄取两行并把水位线停在 EOF；
2. 用同长度内容替换文件，保留第一行不变，只改第二行；
3. 再次扫描。

实际结果：generation 仍为 0，扫描从旧 EOF 返回，随后新 stamp 覆盖旧 stamp；第二行的新内容以后也不会再读。现有“独占句柄”只证明完全不变文件走快路径时不会 open，未覆盖“stamp 已变但首行与长度相同”的替换。

临时回归及运行命令：

```powershell
cargo test -p tokly-adapter-claude --test stream_generation file_identity_discontinuity_with_an_unchanged_head_bumps_the_generation -- --exact --nocapture
```

结果：失败，generation 实际 0、期望 1。修复验收应同时保留独占句柄快路径和本替换反例。

#### B2. API publish 半发布——必须修复

`ApiPeriodCycle::publish` 对前 N-1 条调用 `store.ingest(obs, None)`，只把水位线挂在最后一条；它没有调用已有的 `ingest_batch`。构造两事件周期，让第二条在 fold 中失败。

实际结果：第一条 observation、projection、子表与 dirty session 已提交，第二条失败，周期水位线不存在。进程在事件间崩溃有相同终态，违反“任何页失败都不发布”。

```powershell
cargo test -p tokly-core --test ingest_api_period a_publish_failure_does_not_leave_a_partial_period_visible -- --exact --nocapture
```

结果：临时回归失败，首事件完整残留。修复应把整周期 reconcile、fold 与水位线放进一个事务。

#### B3. API 空新代不撤销旧代缺席键——必须修复

构造 generation 0 成功发布事件 `api-a`，再让 generation 1 成功发布同一封闭周期的空结果。实际只推进水位线并 seal 周期，`api-a` 仍在 projection/report 中。成功枚举的整周期是 reconcile 边界，当前实现只有 upsert，没有为旧代缺席键生成删除/排除证据。

复现方式：在 `ingest_api_period` 集成测试依次 publish 上述两代，然后断言第二代后 `usage_events` 不再计入 `api-a`；当前断言失败。修复必须同时覆盖“非空→空”和“非空→缺少一个键”。

#### B4. SQLite 三机制与 pending——核心分离通过，端到端仍阻断

`RoundReader`、`SafetyHorizon`、`Reconciliation` 是三个独立类型；现有真实 SQLite 回归分别覆盖一致快照分页、同毫秒边界回退、horizon 外回填、指纹代际断裂，定向测试通过：

```powershell
cargo test -p tokly-core --test ingest_sqlite_live -- --nocapture
cargo test -p tokly-core --test ingest_pending -- --nocapture
```

但 workspace 中尚无 OpenCode/Cursor 生产 adapter 把三机制与 pending 组合成一轮发布。更严重的是 `pending_messages` 只持久化 key、时间和 payload hash，不持久化当前 position 或可定稿 payload：若源工具在下一轮前删除 pending 行，`outstanding` 能给出 id、`read_by_id` 却返回空；本轮既无法把它放进 `PendingFloor`，也无法用最后 payload stale-finalize，随后水位线可以越过它。需补“pending 源行消失”的端到端回归并决定持久化/留证策略。

### C. 计价不可逆面

**判无洞项：** `compute.rs` 使用 i128 精确累加，各 `price_kind` 由 `BTreeMap` 以与存储字符串一致的字典序遍历，最后一次 round-half-even；property tests 的舍入可复现、遍历顺序无关、reprice 幂等 3/3 通过。`skipped` 只由 pricing worker 落章；普通 reprice 只在实际改变时推进 `data_version` 并把受影响的非 frozen session 置 dirty，无变化不推进。

```powershell
cargo test -p tokly-pricing --test properties -- --nocapture
```

#### C1. reprice 越过 pruned/frozen 边界——必须修复

reprice 分页扫描全部 `usage_events`，UPDATE 没有 `observations_pruned_at IS NULL` 或 frozen-session guard。临时反例实际观察到：

- pruned event：`(NULL,pending,NULL)` 被改成 `(3000,computed,bundled:0.1.0)`；
- frozen session 的 event 同样被改价，但 dirty 标记逻辑排除 frozen session，永久 session summary 与 event 永久分叉。

复现：在 `tokly-pricing/tests/reprice.rs` 分别插入已 pruned event、属于 frozen session 的 event，导入可匹配价格后调用 `reprice`，逐列比较调用前后。两个临时断言均失败。修复需按 ADR-0002 的“四入口统一”让两类键全列零触碰。

```powershell
cargo test -p tokly-pricing --test reprice repricing_does_not_rewrite_a_pruned_projection -- --exact --nocapture
cargo test -p tokly-pricing --test reprice repricing_does_not_rewrite_events_of_a_frozen_session -- --exact --nocapture
```

#### C2. priced-at-snapshot 转正入口不可达——必须修复

ADR-0015 要求以后补到更早价格历史时，`priced-at-snapshot` 可 reprice 为正常 `computed`。公共 `import_price_table` 却拒绝早于/等于当前首条 `effective_from` 的导入；已有转正测试用裸 SQL UPDATE 绕过公共 API，证明的是内部算法，不是用户可达行为。

```powershell
cargo test -p tokly-pricing --test reprice an_earlier_price_can_be_imported_through_the_public_history_api -- --exact --nocapture
```

结果：临时回归失败，错误为 `cannot import an earlier or equal effective_from ...`。

### D. data_version 递增谓词

**判无洞项：** duplicate 与低 normalizer version 不推进版本；reprice、compact、dirty 重算在实际改变查询结果时推进，无变化时不推进。复审把低版本断言补入 `stale_normalizer_version_is_a_zero_change_skip` 并保留。

```powershell
cargo test -p tokly-core --test fold_rules stale_normalizer_version_is_a_zero_change_skip -- --exact --nocapture
```

#### D1. health 可见提交不推进——必须修复

ADR-0019 定义“任何改变查询可见结果的提交”递增，并明列 `health` scope；`tokly doctor` 查询 `ingest_errors`、pending、watermarks/source instances。`record_ingest_error` 等独立 writer 却不 bump。

```powershell
cargo test -p tokly-core --test data_version a_new_health_finding_advances_the_generation -- --exact --nocapture
```

结果：临时回归失败，`ingest_errors` count 从 0 变 1，`data_version` 仍为 0。同类独立 watermark/stamp 与 pending 写也需统一审计。若团队坚持这些表不属于主版本，必须先用新 ADR 定义独立、可订阅的 health version，不能让同一 `(data_version, scopes=[health])` 对应不同结果。

### E. compact 四入口不可变

**判无洞项：** ingest/replay 对 pruned projection 与 frozen session 有 guard；compact 对 frozen rollup 使用 `WHERE ... frozen_at IS NULL`，重复 compact 在现有固定维度数据上幂等。

#### E1. 维度消失后留幽灵 rollup 键——必须修复

compact 对当前聚合只做 upsert，不删除已经不在当前 aggregation set 中的非 frozen 键。构造同一 event 首次投影到 model/project/agent/tool A 并 compact；随后以更高 revision 把它改到 B，再 compact。

实际结果：rollup truth 为 usage rows=2、event sum=2、tool rows=2、call sum=2；当前 projection truth 均为 1。旧 A 键成为永久幽灵。

```powershell
cargo test -p tokly-core --test compact_lifecycle recompute_removes_non_frozen_rollup_keys_absent_from_the_projection -- --exact --nocapture
```

结果：临时回归失败。按键整片重算必须包含“删掉当前集合没有的非 frozen 键”，同时继续跳过 frozen 键。

### F. report=sessions 等值声明

已有“重建后新摄取”和“只改成本”两种测试通过，只证明了对应输入下的数值 SUM。复审加入生命周期与资金覆盖语义后声明被击破。

#### F1. frozen session reactivation 漏事件——必须修复

`store_totals` 的三条 leg 是 clean sessions、dirty-session events、sessionless events。对 frozen clean session，新到 event 仍带原 session key：它不在 dirty leg，不能进入 sessionless leg，clean session 又保持旧 summary。

最小反例实际值：report 为 4 events、input 737、computed cost 1,000,000；event truth 为 5、778、1,000,017。复现方式：冻结已有 session 后 ingest 一个属于同 session 的新胜者事件，再比较 `store_totals` 与事件级 truth；临时回归失败。该事件已有 `frozen-session-reactivated` 证据不等于可以从总量静默丢弃。

```powershell
cargo test -p tokly-cli report::tests::a_reactivated_frozen_session_does_not_hide_the_new_event -- --exact --nocapture
```

#### F2. 部分成本被显示为完整总账——必须修复

schema 明确 `sessions.has_partial_cost=1` 时汇总不可当完整账目读。`Totals` 没有 partial 标志，`store_totals` 丢弃该列，`cost_cell` 直接打印金额。现有 seeded store 即包含 computed 有值/NULL 混合：重建后 `MAX(has_partial_cost)=1`，实际 CLI 仍显示 `computed cost ... total $1.00`，没有 partial/incomplete 提示。

```powershell
cargo test -p tokly-cli report::tests::a_partial_cost_total_is_not_presented_as_a_complete_ledger -- --exact --nocapture
```

结果：临时回归失败。逐字段 SUM 相等不代表资金覆盖语义相等。

**其他攻击：** priced-at-snapshot 转正被 C2 的公共入口直接阻断；跨日会话本身对全时段 totals 是同一 session 求和，未发现额外数值洞，但它不能修复 frozen reactivation 或 partial-cost 语义缺失。

### G. 验证机构自身

#### G1. P5 oracle 与 SUT 同错——必须修复

ADR-0002 明列以下两类为 same-hash skip，projection 与证据零触碰：

- 同流同代、更高 position、相同 payload hash；
- 跨流或跨 generation、相同 payload hash。

SUT 先选最大 position/最新 generation，再把胜者坐标与胜者时间写入 candidate 并参与整行比较，所以会改写 projection revision/`updated_at`、置 session dirty、推进 `data_version`。P5 模型的 `WinnerIdentity` 同样包含坐标，因此 oracle 随实现一起错。

```powershell
cargo nextest run --locked -p tokly-core --test fold_rules -E "test(same_stream_higher_position_same_hash_is_skip_class_zero_touch) | test(new_generation_same_hash_is_skip_class_zero_touch)"
```

结果：临时契约直译回归 0/2 通过，nextest run ID `30ae42b7-eb14-4300-8bd2-c4fae2178af6`；实际 revision、`updated_at`、dirty 均变化。两个红测取证后已撤回。ADR-0002 已把 same-hash 去重列入跳过类，并把 `usage_events` 全列纳入 P5 零触碰域；应按现行契约同时修 SUT 与 oracle，不能改 oracle 迎合实现。若要改变该语义，必须先追加 ADR 裁决。

#### G2. P6 不是全称性质——必须修复

P6 lifecycle query 只读取 `pruned-key-reobserved` 与 `frozen-session-reactivated`。`json-parse`、`unverified-schema`、`unresolved-mapping`、`unresolved-semantics` 等通用 `record_ingest_error` 路径没有被模型双向枚举；生成器也不产生全部谓词。所谓“12 类角落”在另一套简化计数器中实现，并继承了 G1 的 same-hash 错误条件，不能替代“终态每一条证据行 ⇔ 契约谓词成立”。

验收命令应在补全生成器后继续使用：

```powershell
cargo nextest run --locked -p tokly-core --test evidence
```

但当前绿灯只证明被查询的子集，不证明 P6。

#### G3. 18/18 突变不可审计——必须修复

“compact 突变 18 项全中”只出现在执行者报告和 `dadf610` 提交正文。仓内没有 18 项清单、补丁/运算符、运行命令、日志或 mutant→killer 映射，也没有 mutation harness。因此无法判断是否有等价突变充数，也无法独立复跑。

最低交付：每个 mutant 的单一语义变化、预期 killer 测试、实际命令/退出码；等价 mutant 必须剔除而不是计作“杀死”。

### H. SLO 完整性

#### H1. 基准机构不符合权威规格——必须修复

路线图要求 `bench-3y` 为三年、六源、120 万事件、8 万会话、1,100 天日聚合，所有延迟用 criterion；开发流程再次规定 criterion。当前 fixture 代码明确只生成 Claude，另五源没有生产 adapter；workspace 无 criterion dependency/bench runner。执行者的 wall-clock 只能作诊断，不能给正式 SLO 打勾。

首次导入执行者完整样本仍为 15m36s（十万级 54.6s，目标 <30s）；稳态体积未测。两项已足以阻断 SLO 验收。

#### H2. 独立复跑结果与完整性——未稳定达标

复审只使用完整 `target/bench.db`：

| 核对项 | 值 |
|---|---:|
| observations / events | 1,200,000 / 1,200,000 |
| sessions / watermarks | 80,000 / 80,000 |
| ingest errors / dirty sessions | 0 / 0 |
| session truth vs event truth | 所有 totals 字段一致 |

同一完整库的独立 release 复跑出现两组结果：

- 增量扫描三轮：926.90 / 616.65 / 572.27 ms，80,000 files、0 new/error，所有计数与版本不变；另一轮显式等待进程退出为 2,047.5 ms，未达 `<1s`。
- report：一组冷启 502.15 ms、暖态 51.21–55.20 ms；另一组六次 511.77 / 56.50 / 88.16 / 74.00 / 67.13 / 73.77 ms。冷启稳定未达，暖态通过但偶见 89–157 ms，`<100ms` 不稳定。

复跑纪律：每次等待进程退出后再查库，确认 1,200,000 行、80,000 水位线、0 error/dirty，且扫描前后计数和 `data_version` 不变。`bench2.db` 的 351,090 行再次证明“只看 wall-clock 会把中断当加速”。

正式验收必须补：criterion 分布与置信区间、冷/暖态分开、六源混合、全量导入完整性、compact 后 90d/180d 稳态体积，以及失败时非零退出/完整性断言。

## 五、`prepare_cached` 增量复审
