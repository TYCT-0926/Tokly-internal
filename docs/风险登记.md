## R1 · Bun 单点风险（Windows 风险收敛点）

- **风险**：Windows 侧四类风险同源于 Bun——任一塌方会同时波及 TUI、CLI 单文件与桌面 sidecar。
  1. OpenTUI Windows 质量未证实：issue anomalyco/opentui#152 已关闭（称多数改善），但仍留有闪烁/低帧未完成项（二轮审查 §3 推翻 5：旧"质量差"表述过于确定）——**必须在当前 Windows/Bun 组合实测验证后再定级**；
  2. Bun 未实现 `node:sqlite`：官方参考页长期标 "Not implemented"；旧追踪 issue oven-sh/bun#27092 已 404——**官方文档/主干已前进，Bun 1.3.14 尚未兑现**（二轮审查 §3 推翻 4），本机实测仍 "No such built-in module"；
  3. `bun build --compile` 约 94MB 体积地板（--minify 零效果）；
  4. 桌面 sidecar 孤儿进程（同属 Bun 进程生命周期问题）。
- **证据**：bun.com/reference/node/sqlite；本机 Bun 1.3.14 实测 "No such built-in module"；本机复现编译体积 93.90MB（2026-08-02 审查 §二/§四 盲区 5；二轮审查 §3 刷新）。
- **对冲**：① 显式双驱动适配层（Bun→bun:sqlite / Node→node:sqlite，约 50 行，[ADR-0001](adr/0001-技术栈与运行时.md)）；② 「core 在 Node 24+ 无损运行」为硬约束——Bun 任一环节塌方时 Node 接管，产品不死；③ sidecar 用 Windows Job Object 绑定父子生命周期（[ADR-0004](adr/0004-桌面端分发.md)）；④ TUI Windows 降级预案（降帧/禁特效，不达标引导 Web，诚实标注）；⑤ OpenTUI Windows 实测验证列为 TUI 里程碑（M4）开工前置。
- **状态**：已对冲（架构层）；OpenTUI Windows 质量待当前 Windows/Bun 组合实测。

## R2 · 价格的时间维度

- **风险**：用今天的价目表回算历史成本是 bug 温床——模型调价后，历史月份的成本会被错误改写；`tokly reprice` 的设计初衷（修正历史）反而变成污染源。
- **证据**：LiteLLM 价目持续滚动更新，无生效日期维度（2026-08-02 审查 §四 盲区 3）。
- **对冲**：价目表引入**生效日期**维度——`pricing_history` 表带 `[effectiveFrom, effectiveTo)` 区间，reprice 用 `event.timestamp` 匹配事件时点有效价格（[ADR-0002](adr/0002-数据架构.md) 成本所有权节，二轮修订落地）；远程表无历史时**自建覆盖层**（按抓取时间归档价目快照，`pricingVersion` 已逐事件记录，为重算提供锚点）。
- **状态**：方案已定（DDL 已冻结进 docs/数据库-schema.md），pricing 层实现时落地（M1–M3 内）。

## R3 · 多通道同源双计

- **风险**：同一源的多个采集通道并存（Copilot 的 OTEL / session-state / 个人 API / 企业报告是最完整实例），直接并库必然重复计数。
- **证据**：ccusage #1174（双源共存去重是开放问题）；2026-08-02 审查 §四 盲区 4。
- **对冲**：**用户配置唯一权威通道**；非权威通道照常入库但 `status='excluded'` + `channel` 列区分，默认不进聚合（[ADR-0002](adr/0002-数据架构.md)、[sources/copilot.md](sources/copilot.md) 权威裁决条；Gemini 的 chats/被动 OTEL 双通道同模式）。
- **状态**：已对冲（契约层），待实现。

## R4 · 静默丢数据三点位（方案已定，待实现）

- **风险**：三个已识别的静默丢数据点——① Cursor 库 VACUUM 后 rowid 重编使水位线失效；② OpenCode `finish` 永空的中断轮次永远悬置不结算；③ `(time_updated, id)` 复合游标页边界同毫秒并发漏行。
- **证据**：2026-08-02 审查 §三 P1-7（各点位机制分析）；30 天删源的源上静默丢弃 = 永久丢弃（§四 盲区 6）。**二轮审查 §2 更正：旧"已修"状态错误**——① 旧「水位线 rowid→key 反查」被证伪（`UNIQUE ON CONFLICT REPLACE` 会把锚点 key 移到新 rowid 造成误报；全扫后低 rowid 被旧 revision 拒绝）；② 旧定稿规则未阻止水位线越过未定稿行（过滤后照样推进 = 永久丢数）；③ 2 秒回退仅缓解，不构成"修"。
- **对冲**：方案已定（二轮审查 §2，[ADR-0002](adr/0002-数据架构.md) 水位线节）——① **backup API 副本 + DB generation**（DB 头 change counter + schema cookie + 首 N 行采样哈希；rowid 只在同 generation 内作 position）；② **`pending_messages` 状态机**（每轮先按 ID 重读；finish 非空 / error 非空（已有 token 照常计数）/ 15 分钟陈旧 → 定稿；水位线不越过任何 pending id）；③ **轮内严格分页（单只读事务一致快照）与跨轮 checkpoint 回退分离** + 尾部 safety horizon + 周期全量 reconciliation。兜底可见性靠 `ingest_errors` 表。
- **状态**：**方案已定，待实现**（2026-08-02 二轮更正，非"已修"）；实现时三个点位各至少一个回归用例，并纳入收敛性 property tests（交换/乱序/重放/重建，docs/开发流程.md）。
