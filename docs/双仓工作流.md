# 双仓工作流（内部仓操作手册）

回答一个问题：**两个仓库日常怎么操作**——什么时候提交、怎么写、怎么推、公开仓怎么走 PR、嵌套布局怎么设置。边界规则（什么进哪个仓）见[仓库策略](仓库策略.md)；公开仓的 commit/PR/发布规范以公开仓 `docs/git-规范.md` 与 `docs/开发流程.md` 为权威，本文不复制，只写**内部仓特有的纪律**与**跨仓操作**。

## 一、内部仓的提交纪律

内部仓是文档仓，提交单元不是"改了几个文件"，而是**一个决策批次**：

| 场景 | 一个提交 = |
|---|---|
| 新增/修订 ADR | 一项决策及其连带修订（新 ADR + 被取代旧文的标注 + 受影响活文档的同步）——它们分开就没法单独理解 |
| 审查落地 | 一份审查报告一个提交（档案），处置措施按决策批次另拆 |
| 活文档跟进代码 | 与公开仓对应 PR 同日提交，正文引用该 PR 号 |
| 日常小修 | 错字、死链、勾选状态可合并为一个 `docs: housekeeping` |

**三条硬规则：**

1. **工作会话结束必须提交并推送。** 未提交的工作过夜 = 违规。这不是洁癖：公开仓 3,774 行实现就是以"staged 未 commit、未 push"的状态在一次目录重组中消失的（[风险登记](风险登记.md) R12）。**唯一不依赖本地磁盘的副本是推送过的提交。**
2. **提交即推送。** 内部仓单人维护、无评审流程，commit 与 push 之间没有停留的理由。`git push` 失败（网络/凭据）要当天解决，不留"改天推"。
3. **不随便提交 ≠ 攒着不提交。** "不随便"指的是批次要成逻辑单元、信息要写清动机——不是把 30 份文件堆成一个月再说。方向是**小批次、高频率、每批可独立理解**。

### 提交信息模板

沿用 Conventional Commits（与公开仓一致，降低心智切换），scope 用目录：

```
docs(adr): <决策一句话，英文祈使句，≤72 字符>

<正文：为什么做这个决策 / 依据哪份审查或事件。
不复述改了什么——diff 自己会说。中文可。>
```

scope 表：`adr` / `design` / `research` / `roadmap` / `risk` / `workflow`；跨多类的大批次用无 scope 的 `docs:`。标题英文祈使句（与既有历史一致：`docs: adopt Rust core stack (final review)`）；**禁止任何工具署名与 AI 痕迹**（与公开仓同一红线）。

### 分支

内部仓 **main 直推**为常态——文档仓无 CI 门禁、无外部贡献者，分支只在一种情况用：一次大重构跨多个工作会话、期间 main 不应呈现半成品状态时，开 `docs/<topic>` 短分支，整批完成后合入。不为常规修订开分支——流程为顺畅服务，不为仪式服务。

### 历史卫生

- 推送过的提交**永不 amend / rebase**——内部仓历史是决策档案的一部分；
- 提交前自查：`git diff --staged` 过一遍，确认没有半成品段落、没有临时笔记混入；
- 临时工作文档（如公开仓同步清单）允许入库，用途完成后**删除文件并提交删除**——git 记得它，工作区不留考古层。

## 二、嵌套双仓的物理设置（一次性，可执行）

布局：`E:/Axiom/Tokly` = 公开仓工作树；`E:/Axiom/Tokly/internal/` = 私有仓（独立 `.git`）。**当前公开仓工作树尚未恢复，恢复时按以下顺序执行，防线先于内容：**

```bash
# 1) 恢复公开仓（克隆到临时名，再把 internal/ 移进去，避免任何一步覆盖 internal）
cd /e/Axiom
git clone https://github.com/TYCT-0926/Tokly.git Tokly-restore
mv Tokly/internal Tokly-restore/internal
rm -rf Tokly && mv Tokly-restore Tokly
cd Tokly

# 2) 忽略与排除（双层：.gitignore 随仓分发，info/exclude 本地兜底）
grep -qx '/internal/' .gitignore || echo '/internal/' >> .gitignore
echo '/internal/' >> .git/info/exclude

# 3) AI 协作文件转本地（可见性与痕迹控制，见仓库策略）
printf '/CLAUDE.md\n/AGENTS.md\n' >> .git/info/exclude
git rm --cached --ignore-unmatch AGENTS.md CLAUDE.md   # 文件留磁盘，仓库不跟踪

# 4) 泄漏拦截 hook（internal/ 路径 + AI 协作文件）
mkdir -p .githooks
cat > .githooks/pre-commit <<'EOF'
#!/bin/sh
staged=$(git diff --cached --name-only)
echo "$staged" | grep -q '^internal/' && { echo 'BLOCKED: internal/ paths.' >&2; exit 1; }
echo "$staged" | grep -Eq '^(AGENTS|CLAUDE)\.md$' && { echo 'BLOCKED: AI collaboration files are local-only.' >&2; exit 1; }
exit 0
EOF
chmod +x .githooks/pre-commit
git config core.hooksPath .githooks
```

按名单 grep 内部文档名的检查放**本地 pre-push hook**，不进公开 CI（名单入公开配置即泄密）；公开 CI 只查 `internal/` 前缀。公开提交的作者邮箱配置 GitHub noreply：`git config user.email '<id>+<user>@users.noreply.github.com'`。

CI 侧加同规则检查 + 私有文件名单 grep（防 `--no-verify` 绕过），条目在[公开仓同步清单](公开仓同步清单-2026-08-03.md) §0。

### 构建产物与忽略清单

公开仓 `.gitignore` 的标准件（`target/` 即 Cargo 构建目录，属于此列）：

```
/target/          # Cargo 构建产物——最大的一块，也是 git clean 诱惑的来源
node_modules/
dist/
coverage/
*.local.*
.DS_Store
Thumbs.db
/internal/        # 私有仓，见仓库策略
```

`target/` 与 `node_modules/` 只该用工具自己的命令清理：**`cargo clean` / `pnpm store prune`**。需要 git 清理未跟踪文件时，唯一允许的形式是：

```bash
git clean -xdf -e internal    # 永远带 -e internal；-xdff 全局禁用
```

`git clean -xdff` 会删除 ignored 目录——包括整个 `internal/`。这条禁令写进了 [AGENTS.md](../AGENTS.md) 红线与公开仓 git-规范（待同步）。

## 三、公开仓的提交与部署（恢复后生效）

公开仓走标准开源流程，权威文档在公开仓侧，此处只列骨架与内部仓的衔接点：

1. **分支**：`feat/<scope>` / `fix/<scope>` 短分支（<3 天），squash merge 入 main；main 永远绿、永远可发布。
2. **PR 粒度**：一件事、<400 行 diff 为宜。大特性拆批次的规则见下节"工作拆分"。
3. **PR 自查衔接内部仓**：涉及数据契约 → 内部 schema/ADR 同日提交；涉及跨仓概念 → 按[文档规范](文档规范.md)跨仓事实映射表核对镜像方。PR 描述引用「内部 ADR-NNNN」文字，**不给内部链接**。
4. **CI 全绿才可合**：fmt / clippy `-D warnings` / nextest / 三平台构建 + 各专项门禁（DDL 一致性、样式纪律、泄漏拦截）。
5. **部署 = 发布流水线**（[ADR-0013](adr/0013-分发信任链.md)，不复制）：release-plz 开 release PR → 合入 → tag → CI 三平台构建（cargo-dist + Tauri）→ 签名与公证 → 更新清单签名 → npm publish + GitHub Release。内部仓无部署概念——推送即完成。

## 四、工作拆分（从任务到提交）

大工作如何切成可评审的批次——原则是**每个批次独立可验证、失败可单独回滚**：

1. **纵切优先于横切**：按"一条端到端能力"拆（一个 adapter、一张表及其测试、一个组件及其门禁），不按"先写所有类型、再写所有实现"拆——横切批次无法单独验证。
2. **契约先行成批**：schema/DTO/spec 的变更独立成批先行合入（配一致性测试），实现批次跟进——契约批次小而关键，评审密度最高。
3. **重构与功能永不同批**：先重构（行为不变，测试证明）后功能，两个 PR。
4. **文档随批**：行为变更的批次必须含活文档更新，否则 CI/review 打回（文档规范门禁）。
5. 前端的 **code splitting**（构建产物层面的代码分割）是技术决策不是工作拆分，见 [ADR-0001](adr/0001-技术栈与运行时.md) 前端数据与导航层一节：路由级分包 + ECharts 按需注册 + 非首屏组件懒加载。
