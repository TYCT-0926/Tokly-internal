# 仓库工作流（操作手册）

回答一个问题：**这个仓库日常怎么操作**——什么时候提交、怎么写、公开仓怎么走 PR、防线怎么重装。边界规则见[仓库策略](仓库策略.md)；公开仓的 commit/PR/发布规范以`docs/git-规范.md` 与 `docs/开发流程.md` 为权威，本文只写维护者侧的操作与私有目录的纪律。

## 一、公开仓（唯一远端）

- **提交纪律**：Conventional Commits，标题英文祈使句 ≤72 字符，正文写"为什么"；一个提交一个逻辑单元；**零 AI 痕迹**（hook + CI 双层拦）。
- **节奏**：上线前允许 main 直推小型 chore；**进入实现阶段（阶段一起）一律 `feat/<scope>` 短分支 → PR → CI 全绿 → squash 合入**；PR 一件事、<400 行 diff 为宜。
- **会话末必推送**：未推送的工作等于不存在（全局 CLAUDE.md §5；3,774 行的教训）。
- **身份**：本仓已配 noreply 邮箱，换机器后重配：`git config user.email 'TYCT-0926@users.noreply.github.com'`。
- **部署** = 发布流水线（内部 ADR-0013）：release-plz → tag → cargo-dist/Tauri 三平台 → 签名公证 → npm + GitHub Release。

## 一·五、worktree 删除纪律（2026-08-04 事故后固化）

并行执行者的 worktree 内可能存在**指向 `internal/` 的 NTFS junction**（DDL 一致性测试需要）。MSYS2 的 `rm -rf` 会**跟随 junction 递归删除目标内容**——2026-08-04 因此丢失整个 `internal/`（含其 .git）。

- 删除 worktree **一律用 `git worktree remove`**；
- 报 "Directory not empty" 等错误时**停下查明原因**（多半正是残留 junction 或未清理产物），**绝不用 `rm -rf` 兜底**；
- 确需手工删除：先 `Get-ChildItem -Force | Where-Object LinkType` 列出链接并逐个 `Remove-Item` 解除，再删目录；
- **`internal/` 每批提交后必推远端**——单仓模型把它降为"可选备份"是这次损失被放大的直接原因。

## 二、私有目录 `internal/`

- 定位：本地笔记与战略文档，**永不提交到公开仓**；放什么格式都行（.md/.docx/图片）。
- 自带纯本地 git：改动后 `git -C internal commit` 留历史即可，**无推送义务**（原私有远端为可选备份，删不删随意）。
- 大批文档改动仍按"决策批次"成组提交（历史可读性），scope 用目录：`docs(adr):` / `docs(design):` / `docs(research):` 等。

## 三、防线清单与重装（换机器 / 重新 clone 后执行）

当前已装（2026-08-03）：`.gitignore` 含 `/internal/`（随仓分发）✓ · `info/exclude` 含 `/CLAUDE.md` `/AGENTS.md` ✓ · pre-commit hook ✓ · noreply 邮箱 ✓ · hook 双向验证（加回被拦/删除放行/正常文件放行）✓。

重装脚本（在公开仓根目录）：

```bash
git config user.name 'TYCT'
git config user.email 'TYCT-0926@users.noreply.github.com'
printf '/CLAUDE.md\n/AGENTS.md\n/docs/\n' >> .git/info/exclude
cat > .git/hooks/pre-commit <<'EOF'
#!/bin/sh
# Identity: public commits must use the GitHub noreply address.
email=$(git config user.email)
case "$email" in
  *@users.noreply.github.com) ;;
  *) echo "BLOCKED: user.email must be a GitHub noreply address (got: '$email')." >&2; exit 1 ;;
esac
# Block adding/modifying local-only paths; deletions are always allowed.
bad=$(git diff --cached --name-status | awk '$1 != "D" { print $NF }' | grep -E '^(internal/|docs/|AGENTS\.md$|CLAUDE\.md$)')
[ -n "$bad" ] && { echo "BLOCKED (local-only): $bad" >&2; exit 1; }
exit 0
EOF
chmod +x .git/hooks/pre-commit
```

> 2026-08-03 实发事故：并行执行者把仓库 `user.email` 覆写为占位 `a@b`，一笔提交带占位身份进入公开 main（已 amend 洗净、两分支同树 rebase）。防线因此从"配置"升级为"机器强制"——hook 第一段校验身份，配置漂移在提交时响亮失败而不是静默入库。

**清理禁令**：`git clean -xdff` 全局禁用（删 ignored 目录 = 删 `internal/` 与 `target/`）。构建产物只用 `cargo clean` / `pnpm store prune`；确需 git 清未跟踪文件：`git clean -xdf -e internal`。

**破坏性操作前**（`rm -rf` / 对仓库的 `mv` / `reset --hard`）：先 `git status` 清点未提交工作——公开仓与 `internal/` 都要看。

## 三·五、并行执行者的 worktree 生命周期（2026-08-04 固化）

并行的多个 AI 执行者**一人一个 git worktree**（`git worktree add ../Tokly-<scope> -b feat/<scope> main`）——它是同一仓库的另一视图，**不是第二个项目、不是散落副本**：

1. **派发时创建**：Prompt 内写明 worktree 命令；共享主目录只允许一个执行者。
2. **代码只存在于分支上**：worktree 目录本身没有独立内容——所有提交都在 `feat/*` 分支，随时可从任何视图看到。
3. **复审通过 → squash 合入 main**：那一刻工作进入唯一最终归宿（`E:\Axiom\Tokly` 的 main 历史）。
4. **合入后立即清理**：`git worktree remove ../Tokly-<scope>` + 删分支——不留任何目录级残余。维护者在关闭记录里核对清理完成。

范例：阶段二在 feat/core-slice 七轮打磨，最终一笔 `02603ec` 进 main，分支删除；阶段五的 `../Tokly-design-tokens` 在合入后同样移除。**任何时候"最终文件"只有一份：main。**

## 四、工作拆分（从任务到 PR）

- **纵切优先于横切**：按"一条端到端能力"拆（一个 crate 及其测试、一个组件及其门禁），横切批次无法单独验证。
- **契约先行成批**：schema/DTO/spec 变更独立成批先行（配一致性测试），实现批次跟进。
- **重构与功能永不同批**。
- **文档随批**：行为变更必须同批更新活文档，否则打回（文档规范门禁）。
- 阶段级的任务包与验收见[执行计划](执行计划.md)。
