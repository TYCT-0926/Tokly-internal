# ADR-0019: 数据新鲜度与变更传播

- 状态：accepted
- 日期：2026-08-04

## 背景

三端都是**实时刷新**的观察面：daemon 在后台持续摄取，Web / TUI / 桌面窗口需要及时反映新数据。但现状（2026-08-04 实测 `crates/tokly-server`、`tokly-service`）只有两样东西：

- SSE **只发心跳**（`heartbeat`），不携带任何变更信息；
- DTO **零版本概念**——没有任何字段能表达"这份数据算到哪一刻"。

[ADR-0001](0001-技术栈与运行时.md) 的「前端数据与导航层」写了"SSE 事件到达 → 按 key 失效 → 重取"，但**事件本身的内容、失效的粒度、漏事件怎么办、多块数据是否同一时刻**全部未定义。这不是缺功能，是一类基础性 bug 的温床：

| 缺什么 | 产生的 bug |
|---|---|
| 变更事件不带信息 | 要么全量重取（浪费、闪烁），要么不知道该重取什么（陈旧） |
| 无版本号 | SSE 断线重连期间的变更**永久丢失**——客户端不知道自己错过了什么 |
| 无一致性锚点 | 概览的 KPI、趋势图、热力图各自查询，可能**跨越两次摄取提交**——三块数据互相矛盾（总量对不上明细） |
| 无陈旧语义 | daemon 挂了、降级只读、重取中——UI 一律显示为"正常数据"，用户看着过期数字做决定 |

## 决策

### 1. 单调数据版本（data_version）

数据库内维护一个**单调递增的数据版本**，语义是"已提交的写入代次"：

- 每次**写事务提交**时 +1（摄取批、reprice、compact、dirty 重算——任何改变查询可见结果的提交）。2026-08-05 复审 D1 裁决：**谓词域 = fold 域 ∪ health 域**——`ingest_errors`、水位线戳、pending 等诊断可见写同样递增（scope 标 `health`）；不另立健康版本；
- 与 `schema_version`（结构版本，进程协商用）正交，互不替代；
- 存放：`meta` 单行表（`data_version INTEGER NOT NULL`），与写事务同事务更新——**不额外引入协调成本**，因为写连接本就唯一且串行（[ADR-0012](0012-进程与本地服务.md)）。

### 2. 查询结果携带版本，且**复合视图单版本**

- 每个查询 DTO 顶层带 `data_version`——这份数据算到哪一刻，客户端可判断新鲜度；
- **一屏所需的多块数据必须在同一只读事务内计算**（SQLite WAL 快照隔离天然提供），返回同一个 `data_version`。禁止"KPI 一次查询、趋势另一次查询"式拼装——那正是"总量对不上明细"的来源；
- service 层因此提供**面向屏的复合查询**（overview / drilldown），而不是让客户端拼多个原子查询。

### 3. 变更事件携带版本与受影响范围

SSE / Tauri events / TUI 进程内订阅**发同一种事件**：

```
{ data_version: u64, scopes: ["events","sessions","rollups","quota","health"] }
```

- `scopes` 是**粗粒度**的（表族级，不是行级）——客户端据此决定失效哪些 Query key，避免全量重取；
- 粗粒度是有意的：行级精确失效的复杂度换不来体感差异，而错误的行级失效会产生极难排查的陈旧。

### 4. 漏事件的检测与恢复（断线重连的正确性）

客户端**持有 last_seen_version**：

- 收到事件时若 `event.data_version > last_seen + 1` → **中间有漏**，执行全量失效（不试图补差）；
- SSE 重连后，服务端在**首个事件**里发送当前 `data_version`，客户端同样按上条判断；
- 连接建立时的首个查询即建立基线。**"漏了就全量重来"是刻意的**：补差机制的复杂度与出错面远大于一次多余的重取，而重取在本地数据上是毫秒级的。

### 5. 陈旧与降级必须可见（不静默）

三态在 DTO 与 UI 上都必须可区分：

| 态 | 判据 | UI 表现 |
|---|---|---|
| 新鲜 | 已收到 ≥ 当前 `data_version` 的数据 | 正常 |
| 重取中 | 已知有更新版本、数据尚未到 | 保持旧值 + 细微进行中指示（**不骨架屏、不闪烁**——数据仍有效，只是不是最新） |
| 陈旧 | 事件流断开超阈值 / daemon 不可达 / 只读降级 / 摄取已停（`lock-integrity-lost`） | 顶栏明确标注"数据可能过期（最后更新 hh:mm）"，**不伪装成实时** |

摄取停止（ADR-0012 的所有权失效）属陈旧态的一种，走同一条展示路径。

### 6. TUI 与桌面：同一机制，不同传输

- **TUI 同进程**：直接订阅 service 的变更广播（`tokio::sync::broadcast` 或等价），**不轮询**；渲染节流（10fps 合帧，组件规格 §13）在订阅之后，两者正交——节流控制"多久画一次"，版本控制"画什么"；
- **降级只读直连**（daemon 不可达）：无事件源 → **低频轮询 `data_version`**（默认 5s）作为唯一例外，且界面常驻陈旧标注；
- **桌面 Tauri**：IPC events 承载同一事件结构，与 SSE 逐字段一致（DTO 单一来源，ts-rs 生成）。

## 为什么现在做

七A（Web UX 竖切）与九（TUI）**正在施工数据层**。版本与事件结构是 DTO 契约的一部分——ts-rs 生成、前端消费、TUI 订阅三处同时依赖它。现在定，成本是几个字段；等两端各自把"刷新"实现完再统一，等于两端返工，且期间写出的每个组件都建立在错误的新鲜度假设上。

`data_version` 入 schema 也是**入库后不可逆**类改动（需要迁移），恰在冻结门窗口内。

## 代价与备选

- **代价**：每次写事务多一次单行 UPDATE。写连接唯一且串行，无锁竞争；量级相对于批量摄取可忽略。
- **备选一：客户端定时轮询，不做事件。** 弃选：要么轮询过密（浪费 + 本地 IO 抖动），要么过疏（体感迟钝）；且仍需版本号来避免无谓重渲染——省不掉核心机制，只省掉了推送。
- **备选二：行级/键级精确失效。** 弃选：复杂度与出错面显著上升，而本地重取是毫秒级——**粗粒度失效 + 快速重取**在本产品的数据规模下是更优解。
- **备选三：用 SQLite 的 `data_version` PRAGMA / WAL 帧号。** 弃选：它反映的是**页面级写入**而非"逻辑提交代次"，checkpoint 等内部行为也会改变它，语义不可控且不跨连接稳定。自建单调计数器语义清晰、可测试。
- **代价**：`scopes` 粗粒度意味着某些场景会重取用不到的数据。接受——错误的精确失效比多余的重取危险得多。

## 后果

- [数据库-schema](../数据库-schema.md) 增 `meta` 单行表（`data_version`），写事务同事务递增；
- `tokly-service` 增复合查询（overview / drilldown）与变更广播；DTO 顶层增 `data_version`，事件结构入 ts-rs 生成面；
- `tokly-server` 的 SSE 从纯心跳升级为**心跳 + 变更事件**（心跳保留：用于检测连接存活 → 陈旧态判定）；
- [组件规格](../design/组件规格.md) 增「新鲜度三态」的展示规则（顶栏陈旧标注、重取中的细微指示）；
- 七A 与九的施工按本 ADR 落地；[编排规格](../design/编排规格.md) §四 的数据级联在**同一 `data_version`** 内编排。
