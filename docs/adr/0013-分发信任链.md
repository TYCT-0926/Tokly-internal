# ADR-0013: 分发信任链——签名、更新与版本工具

- 状态：accepted
- 日期：2026-08-03

## 背景

[ADR-0006](0006-开源发布.md) 定了渠道（npm 启动器 + GitHub Releases）与版本工具，但漏了三件在真实分发链路上会直接卡住的事：

1. **代码签名与公证**：未签名的 Tauri 应用在 macOS 被 Gatekeeper 拦下、在 Windows 触发 SmartScreen。这不是体验问题，是装不上——而桌面端是 M5 的全部产出。
2. **更新通道**：六源解析器是本项目最易腐坏的部分，上游格式一变用户就在拿错数据。没有更新通道，修复的送达速度取决于用户什么时候想起来升级。
3. **版本工具与栈不匹配**：changesets 是 npm 包版本工具，而产品是 Cargo workspace 加一个二进制启动器包——它是全栈 TypeScript 时代的遗留，与 uPlot、fsnotify 同族。

## 决策

### 签名

| 平台 | 方案 |
|---|---|
| macOS | Developer ID 签名 + notarization + hardened runtime；CI 用 App Store Connect API key，凭据进仓库 secrets |
| Windows | **首发不购证书**：提供 SHA-256 校验和与 winget 清单，下载页明示 SmartScreen 警告的成因与校验方法；**1.0 前引入 Azure Trusted Signing**（订阅制，无需 EV 硬件令牌） |
| Linux | 不签名；提供 `.deb` / `.AppImage` / `tar.zst` 与校验和 |

Windows 首发不签名是**成本换时间的显式取舍**，其代价（首次安装的信任摩擦、部分用户直接放弃）记入[风险登记](../风险登记.md) R11。

### 更新（只定原则，不定实现）

- 更新清单由发布流水线签名，公钥内置于产物——**更新通道本身必须可验证**，否则它是比不更新更大的风险面。
- **检查更新默认开启，安装一律由用户确认**。本地优先的工具不应在用户不知情时改变自己。
- **解析器版本告警独立于应用更新**：adapter 遇到未声明过的源格式版本时立即告警（[ADR-0014](0014-诊断与格式演进.md)），不等用户升级才发现数据不全。这条比自动更新更重要——它让"数据可能不完整"这件事在修复送达之前就是可见的。

桌面端用 Tauri updater，CLI 走安装器 self-update 或提示；具体实现在 M5 落地时定。

### 版本与发布工具

- **release-plz 取代 changesets**：Cargo workspace 原生，按 Conventional Commits 自动生成 CHANGELOG、bump 版本、开 release PR；npm 启动器包版本由同一流程同步写入。
- 产物构建保留 cargo-dist（三平台原生 CLI）与 Tauri 安装包。
  > cargo-dist 的维护状态属会过期的外部事实，**冻结前须核实并在本节记录核实日期与版本**。若不可用，回退方案是 `cargo xtask dist` + CI 矩阵自建，产物形态与安装脚本不变——该回退是本决策可接受的前提。

### 版本策略

语义化版本；0.x 阶段 minor 允许破坏性变更。**1.0 门与[路线图](../路线图.md) M2 对齐**（Dashboard v1 + 配额窗口初版稳定），修正 ADR-0006 原文"1.0 在 M3 Dashboard 稳定后"与路线图 Dashboard 在 M2 的不一致；1.0 的具体验收项在路线图 M2 收尾条目列出。

## 为什么现在做

签名不是发布前一周能补的事：它决定 CI secrets 结构、决定是否需要一笔年度支出、在 macOS 上还决定构建产物的形态（hardened runtime 影响链接与权限声明）。M5 开工时才发现要签名，等于让桌面端里程碑带着一个采购流程一起延期。

版本工具则相反——它现在改成本几乎为零（还没有 release 历史），M1 之后改要迁移 CHANGELOG 与 tag 惯例。

更新只定原则不定实现，是因为实现细节依赖 M5 的桌面端形态，现在定会是猜测。

## 代价与备选

- **代价**：macOS 签名需要 Apple 开发者计划年费与一套凭据轮转流程；CI 复杂度上升。这是分发到普通用户的准入成本，没有替代路径。
- **备选一：Windows 首发即购 EV 证书。** 弃选理由：EV 需要硬件令牌，与无人值守 CI 冲突，且费用显著；Azure Trusted Signing 是更合适的形态，但把它压到 1.0 前而非首发，是为了不让分发采购阻塞 M5。
- **备选二：完全不做桌面签名，只发 CLI 与 Web。** 弃选理由：桌面端（托盘 + Widget）是三端形态的一部分，也是[竞品调研](../research/竞品调研.md)里"没人占住的位置"之一，放弃它等于放弃一块差异化。
- **备选三：保留 changesets，只是配合 Rust 手工 bump。** 弃选理由：两套版本真相源必然漂移，而"版本号与 CHANGELOG 由 release PR 统一维护"已经是既定纪律。
- **代价**：release-plz 依赖 Conventional Commits 的严格执行。这已经是 git 规范的要求，代价是把"建议"变成"门禁"。

## 后果

- ADR-0006 的「changesets」与「1.0 在 M3」两条被本 ADR 取代；渠道决策（npm 启动器 + GitHub Releases）不变。
- CI 需要三组 secrets：macOS 签名凭据、更新清单签名私钥、（1.0 后）Windows 签名凭据。
- 发布流水线：release PR → tag → 三平台构建 → 签名与公证 → 更新清单签名 → npm publish + GitHub Release。
- 新增风险登记条目 R11（Windows 首发不签名的信任摩擦）。
