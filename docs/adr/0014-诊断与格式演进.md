# ADR-0014: 诊断能力与源格式演进的可见性

- 状态：accepted
- 日期：2026-08-03

## 背景

一个解析六种持续演进的第三方格式的工具，**诊断能力就是支持能力**。`docs/开发流程.md` 自己写着"解析器是本项目最易腐坏的部分"，但全仓没有诊断命令，也没有格式演进的探测机制：`ingest_errors` 只覆盖了"能识别出是坏行"的情况，而格式演进的典型形态恰恰是**结构合法、语义变了**——JSON 解析成功、字段名相同、含义不同，静默产出错数据。

同时"不做遥测"一直是隐含前提（公开仓 README 写 "uploads nothing"），却从未作为决策被记录。隐含立场无法约束将来的自己。

## 决策

### 源格式演进的可见性（本 ADR 的核心）

每个 adapter 声明它**验证过**的 `raw_schema` 版本集合——即 golden fixtures 实际覆盖的集合。遇到集合外的版本：

1. 事件按可解析部分入库，`status = 'excluded'`、`exclude_reason = 'unverified-schema'`——**不猜语义**，与全局 fail-visible 一致；
2. 记 `ingest_errors`，错误码 `unverified-schema` 并带版本标识；
3. UI 顶栏该源的状态点转为"有问题"，数据健康面板给出「检测到 <源> 的新格式版本，该部分用量未计入」；
4. CLI 由 `tokly doctor` 输出同等信息。

这把"解析器腐坏"从一个只能靠用户投诉发现的问题，变成产品自己会说出来的状态。

> 2026-08-03 澄清（阶段二 spec 对齐裁决）：**无独立格式版本字段的源，已验证集合按结构形态定义**（如 usage 为对象且 token 字段为整数这类结构谓词），发布版本号（cliVersion 类）**不作** schema 集合——否则源工具每次发版都会把新用量整批 excluded，与本机制探测语义断裂而非发布节奏的意图相反；版本号记入 `ingest_errors.detail_key` 供排查。有显式格式代际的源照常按代际集合。

> 2026-08-03 澄清（阶段二 spec 对齐裁决）：**无独立格式版本字段的源，"已验证集合"按结构形态定义**（如"usage 为对象且 token 字段为整数"这类结构谓词），发布版本号（cliVersion 类）**不作** schema 集合——否则源工具每次发版都会把新用量整批 excluded，与本机制"探测语义断裂而非发布节奏"的意图相反；版本号记入 `ingest_errors.detail_key` 供排查。有显式格式代际的源（opencode Gen A/B、cursor 3.x 表结构）照常按代际集合。

### `tokly doctor`

单命令输出全局健康：各源的发现路径与实例、格式版本、水位线位置与代际、最近事件时间、坏行/冲突/未匹配定价计数、数据库各层行数与体积、daemon 锁状态、配置校验结果。

它同时是[组件规格](../design/组件规格.md)「数据健康」面板的数据源——**同一份诊断，两种呈现**，不写两遍。

### 日志

`tracing` + `tracing-subscriber`；默认 `warn`，`--verbose` 与 `TOKLY_LOG` 提升等级；落盘至 `<data_dir>/tokly/logs/` 按天轮转保留 7 天。日志**只记指标与位置，不记内容**——与[ADR-0002](0002-数据架构.md)资源纪律同一条红线。

### 不做遥测（显式决策）

无使用统计、无崩溃上报、无任何回传。产品的出站网络只有两处：定价表刷新（可关闭）与用户显式授权的 API 源。**任何新增出站请求都需要新的 ADR**——这条约束的价值全在于它把默认答案定成了"不"。

## 为什么现在做

`unverified-schema` 机制影响两处不可逆的东西：`usage_events.exclude_reason` 的取值域，以及 adapter 的能力声明结构（要多一个"已验证格式版本集合"字段）。两者都在 M0.5 冻结门范围内——冻结之后再加，意味着已入库的事件里没有这个标记，而那批数据恰恰是最早导入、最可能跨越格式代际的。

`tokly doctor` 与日志本身可以晚做，写进本 ADR 是因为它们与上述机制共用同一份诊断数据结构，分开定会得到两套。

## 代价与备选

- **代价**：`status='excluded'` 意味着遇到新格式时用量会**少算**而不是错算。这是有意的取舍：少算是可见的（有告警、有计数），错算是不可见的。产品在这里选择让用户看见缺口。
- **备选一：遇到未知版本按最接近的已知版本尽力解析。** 弃选理由：这正是"结构合法语义变了"最危险的路径——它会产出看起来正常的错数据，且没有任何痕迹。ADR-0002 已经为 OpenCode / Gemini / Copilot 的同类情形定了 fail-visible，本条只是把它推广到"版本未知"这个更一般的触发条件。
- **备选二：只记 `ingest_errors`，仍按 counted 入库。** 弃选理由：错误表没人主动看；聚合数字才是用户看的东西。缺口必须体现在数字上才有意义。
- **代价**：adapter 每次支持新版本都要更新已验证集合并补 fixtures。这正是想要的——它把"我们验证过什么"变成了必须显式声明的事实，而不是靠记忆。
- 日志框架选 `tracing` 不构成取舍（Rust 生态事实标准），写在此处只为避免各 crate 各选一套。

## 后果

- 新增 CLI 子命令 `tokly doctor`；`ingest_errors.error_code` 增 `unverified-schema`；`usage_events.exclude_reason` 取值域增同名项。
- adapter 能力声明增加"已验证格式版本集合"，与 golden fixtures 同 PR 维护——[路线图](../路线图.md) M6 的 adapter 贡献套件把它列入 checklist。
- [风险登记](../风险登记.md) R8（解析器腐坏）的对冲即本 ADR。
- [组件规格](../design/组件规格.md)新增「数据健康」面板与顶栏状态点的第四态。
