# ADR-0008: 订阅配额窗口作为一等公民

- 状态：accepted（2026-08-02 二轮修订，依据 [审查-2026-08-02-二轮](../research/审查-2026-08-02-二轮.md) §1/§2：usedPct 允许 null、补 provenance 五列、Claude 本地日志只承诺 activity+burn rate、M3 配额范围收敛为 Claude+Codex）
- 日期：2026-08-02

## 背景

目标用户主体是订阅用户（Claude Pro/Max、ChatGPT Plus/Pro 等），他们每天真实遭遇的问题是**撞配额窗口上限**（"5 小时窗口还剩多少"），而不是等效美元账单。证据与论述见 [审查-2026-08-02](../research/审查-2026-08-02.md) §三 P0-4 与 §四 盲区 1：

- 官方 `/usage` 类面板已杀死"单工具配额监控"生态位，但**没人做跨工具聚合**；
- 这个赛道活得最好的功能全是"油表"（剩余量、燃烧率）而非"账本"（历史账单）；
- Codex rollout 里就躺着官方 `rate_limits` 快照，采集成本几乎为零（见公开仓 `docs/sources/codex-cli.md`）。

原数据模型只有"事件 → 成本"一条轴，配额窗口不在模型内——这是被审查推翻的隐性决策。

## 决策

### 新表 `quota_snapshots`

配额观测是与 UsageEvent 正交的一等数据，独立成表（不写进 usage_events，避免污染用量聚合）。规范 DDL 见 [数据库-schema](../数据库-schema.md)，逻辑列：

| 列 | 语义 |
|---|---|
| `source_instance_id` | 源实例（同 ADR-0002 身份模型） |
| `limit_key` | **稳定限额键**（如 `codex:primary` / `codex:secondary` / `claude:5h` / 源原生 limit_id 规范化）——同一逻辑限额跨事件的键必须稳定 |
| `observed_at` | 观测时刻（epoch_ms UTC） |
| `used_pct` | 已用百分比（0–100；**允许 null**——只有官方端点直给或用户显式配置容量时才生成百分比，见下） |
| `used_amount` / `unit` | 观测用量及其单位（`tokens` / `requests` / `credits` / `pct`）；本地重建只承诺这一层 |
| `capacity` | 窗口容量（unit 计量）；未知/动态为 null |
| `window_minutes` | 窗口长度（分钟，如 300）；未知为 null |
| `resets_at` | 窗口重置时刻；未知为 null |
| `provenance` | **溯源**：`'official'`（源/官方端点直给）/ `'local-estimate'`（本地日志重建）/ `'user-configured'`（用户显式配置容量/规则） |
| `rule_version` | 窗口规则版本（本地重建规则属外部事实，硬编码必须带版本，改规则不发版也能修） |
| `confidence` | 置信度 `'high'/'medium'/'low'`（UI 降级依据） |
| `raw` | 原始快照 JSON（溯源与字段演进兜底） |

### 采集路径（按源）

- **Codex（权威快照，零推算，`provenance='official'`）**：rollout 的 `token_count` 事件自带 `rate_limits`（limit_id + 主/副限额百分比快照），adapter 摄取用量时顺手落 `quota_snapshots`——官方数据，直接可信。**采集独立于 token 跳过逻辑**（info==null / 累计未前进 / 五项全 0 的 token_count 只要带 rate_limits 就照采，见公开仓 `docs/sources/codex-cli.md`）。
- **Claude Code（本地重建，`provenance='local-estimate'`，只承诺 activity + burn rate）**：源不落配额数据。由本地事件流重建 5 小时滑动窗口的 **observedUsage（used_amount + unit）与燃烧率（burn rate）**（窗口规则按官方公开口径硬编码、带 `rule_version`、可配置覆盖）。**本机日志看不到其他设备、Claude.ai 活动、动态容量与服务端策略，推不出官方 usedPct**（二轮审查 §1）——因此 `used_pct` 一律 null、`capacity` null；只有官方端点直给（`provenance='official'`）或用户显式配置容量（`provenance='user-configured'`）时才生成百分比。M2 UI 展示 observedUsage + unit + burnRate，标注推算，永不与官方快照混排声称精确。
- 其余源有能力即补（Copilot API 的 premium-request 用量、OpenCode 无），能力矩阵照常声明，没有就不硬撑。

### 产品定位：记账本 vs 油表

Tokly 的差异化组合是**永久历史仓库（记账本）+ 跨工具配额窗口（油表）**：

- 记账本回答"钱花哪了"——ccusage 们的领地，我们靠持久化与三端胜出；
- 油表回答"还能烧多久"——官方单工具面板只照得到自己，跨工具聚合是空位；
- 二者共用同一摄取管线，配额窗口不进 usage_events 但共享 daemon/调度/UI 基础设施。

### 路线图位置

M1 落 `quota_snapshots` 表（schema 先行）；M2 随 Dashboard v1 出配额窗口初版 UI（Claude 5h 窗口本地重建的 activity + 燃烧率油表，标注推算，不出百分比）；Codex `rate_limits` 快照采集随 Codex adapter 落地；**M3「配额完整化」范围明确只指 Claude + Codex 两源**（Claude 本地重建规则完善 + Codex 官方快照；其余源有能力即补，不作承诺，二轮审查 §2）。详见 [路线图](../路线图.md)。

## 后果

- 数据模型从"事件单轴"变为"事件 + 配额快照双轴"，schema 与查询层一并扩展。
- 配额数据三级溯源（official / local-estimate / user-configured）+ confidence，推算值永远标推算、永不与官方快照混排声称精确——与全局溯源标注原则一致；`used_pct` 的 null 是诚实的"不知道"，不是缺失 bug。
- 窗口规则属外部事实（官方可随时改），硬编码规则必须有 `rule_version` 与配置覆盖口，改规则不发版也能修。
