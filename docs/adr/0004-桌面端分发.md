# ADR-0004: 桌面端分发策略

- 状态：accepted（2026-08-02 二轮修订：Rust 直读上调为 v1 候选方向、M5 决策门、Tauri 边角坑登记）
- 日期：2026-08-02

## 背景

桌面端 = Tauri 2 壳（托盘 + 可钉 Widget + 完整窗口），窗口复用 Web Dashboard 构建产物。核心（Bun/TS）如何随桌面端分发，存在体积与复杂度的权衡。

## 决策

**v1：Tauri sidecar 方案。** `bun build --compile` 产出核心单文件，作为 Tauri sidecar 随应用分发；前端经 Tauri 自定义协议加载，与 sidecar 通过本地 IPC/HTTP 通信。

**体积实测修正（2026-08-02 spike）**：`bun build --compile` 有约 **94MB 的运行时体积地板**（空 hello-world 即 94MB，应用代码只贡献个位数 MB），v1 总安装体积预估修正为 **~100–110MB**（仍小于 Electron 同级应用，但优势收窄）。因此 v1 同步评估两条分发路径：①内嵌 sidecar（开箱即用，~110MB）；②发行 JS 包、依赖用户已有 Bun/Node（体积极小，有运行时门槛）。桌面端可优先用 ②（面向开发者用户），新手安装包用 ①。

**托盘/Widget Rust 直读：上调为 v1 候选方向（2026-08-02 审查 §三 P1-12）**。托盘与 Widget 只需聚合数据，可由 Tauri Rust 侧用 rusqlite 直读同一个 SQLite 文件（聚合 SQL 量小且稳定），完整窗口再按需拉起核心；无 sidecar 场景可降至 10MB 级。配套：聚合查询下沉为**共享 .sql 文件 / SQLite 视图**，TS 与 Rust 消费同一份，避免两套查询逻辑漂移。代价是引入双语言（TS+Rust）维护成本，与界面优先原则需要权衡——**M5 开工时为最终决策门**，届时按 Dashboard 冻结后的查询面实测再定，此前不做承诺。SQLite schema 因此视为跨进程公共契约，变更需迁移脚本，禁止破坏性改写。

**Tauri 边角坑（登记自审查）**：

- macOS 托盘常驻应用需 Accessory 激活策略（`NSApplicationActivationPolicyAccessory`），否则 Dock 图标与焦点行为错乱。
- Linux 透明窗口在部分 NVIDIA 驱动下渲染异常——默认回退不透明，透明仅作显式开启项。
- sidecar 进程清理：Windows 下用 Job Object 绑定父子生命周期，杜绝桌面端退出后 sidecar 变孤儿进程（与 Bun 风险同源，见 [风险登记](../风险登记.md)）。

## 备选及弃选理由

- WebView 内跑核心（sql.js/OPFS）：性能与持久化模型不达标，弃。
- 要求用户独立安装 CLI、桌面端仅做客户端：安装路径割裂，违背开箱即用，弃（但架构上不阻止：桌面端发现已有本地核心时可复用）。

## 后果

- CI 需为三平台产出：Tauri 安装包（内嵌 sidecar）、独立 CLI 单文件。
- sidecar 进程生命周期归桌面端管理：退出清理、崩溃重启、端口只绑 127.0.0.1。
