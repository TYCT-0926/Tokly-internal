# ADR-0020: 形态分发与模块化安装

- 状态：proposed
- 日期：2026-08-04

## 背景

维护者要求：**只用 TUI 就只装 TUI，只用桌面就只装桌面，只用 Web 就只装 Web**，共用同一个数据底座，避免臃肿安装。

现状是单工作区多 crate 但**分发形态未定**：路线图只说"cargo-dist 出预编译包"，没有回答"用户装什么"。若按默认路径走下去，结果是一个把 ratatui + axum + 静态资源全部链进去的胖二进制——TUI 用户被迫携带 Web 资源，Web 用户被迫携带终端渲染栈。

参考实现（2026-08-04 实地考察）：

| 项目 | 形态 | 分发 |
|---|---|---|
| codeburn | 桌面 / Web / 终端 / 菜单栏 | 桌面走平台安装包；其余走 `npx codeburn`、`npx codeburn web`、`codeburn menubar` |
| tokscale | 终端 | Rust 核心 + npm 启动器（`bunx tokscale`）+ Docker |
| openusage | macOS 菜单栏 | 单一原生 app |

两个多形态项目都是**一个核心 + 按形态分发的入口**，没有一个把所有形态塞进单一产物。

## 决策

### 1. 形态 = 独立二进制，核心通过子命令发现（git / cargo 模型）

```
tokly            核心（必装）：scan / report / doctor / config / daemon / compact
tokly-tui        终端界面         →  tokly tui
tokly-web        本地 HTTP 服务   →  tokly web
Tokly.app/.exe   桌面（自带核心，独立安装包，不是插件）
```

`tokly <name>` 在 PATH 上查找 `tokly-<name>` 并 exec；找不到时打印**该形态的安装指令**而不是报错退出。这是 git/cargo 沿用二十年的机制：零动态链接、零 ABI 约束、形态可事后追加而无需重装核心。

### 2. 形态与核心的契约 = 已有的两道版本

形态**不链接核心的 Rust API**，只依赖两样已经存在且已版本化的东西：

- **store schema**（`schema_version` 握手，[ADR-0014](0014-诊断与格式演进.md)）——只读直连时用；
- **service API + DTO**（ts-rs 单一来源）——经 daemon 时用。

版本不匹配时形态**拒绝启动并打印双方版本**（阶段九已实现该行为，快照 `newer_schema_refuses_with_versions` 钉死）。因此"多二进制版本漂移"这个 B 方案的固有风险，在本项目里由既有机制承担，不需要新机制。

### 3. `tokly install <surface>` 作为一等命令

核心内置安装器：按当前核心版本，从 release 拉取**匹配版本**的形态二进制放入同一目录。用户不必知道 cargo、npm 或平台包管理器。

分发渠道并存，各自服务不同人群：

| 渠道 | 命令 | 面向 |
|---|---|---|
| 自安装 | `tokly install tui` | 已装核心的人（主路径） |
| 预编译 | 安装脚本 / cargo-dist | 首次安装 |
| cargo | `cargo install tokly-tui` | Rust 用户 |
| npm | `npx tokly` | JS 生态习惯（两个参考项目都提供） |
| 桌面 | 平台安装包 | 非命令行用户 |

### 4. Web 形态的资源随形态走

前端构建产物（SPA、字体、令牌 CSS）用 `rust-embed` 嵌入 `tokly-web`，**不进核心**。核心保持无 HTTP 服务端依赖（axum 只在 `tokly-web` 与 daemon 的 IPC 面）。

### 5. 桌面是自带核心的完整应用，不是插件

Tauri 产物必须能被非命令行用户双击安装即用，因此它**内嵌一份核心**而非依赖 PATH 上的 `tokly`。代价是桌面用户若同时用 CLI 会有两份核心——用同一个 store 路径与单 owner 锁（[ADR-0012](0012-进程与本地服务.md)）保证不冲突，`tokly doctor` 报告检测到的多份安装。

## 为什么现在做

M1 正在建 CLI 与数据层，`tokly-web` / `tokly-tui` 的 crate 边界与依赖归属**现在划一次成本是零**；等三个形态各自把依赖长进核心再拆，等于三轮返工。分发形态还决定 cargo-dist 配置与 CI 产物矩阵，属于路线图 M4 的前置。

## 代价与备选

- **备选一：单二进制 + cargo features**（`cargo install tokly --features tui,web`）。弃选：预编译包无法按 feature 组合分发——而绝大多数用户走预编译；事后加形态要重装核心；违背"避免臃肿"的原始诉求（下载的仍是全量）。
- **备选二：动态库插件（.so/.dll）**。弃选：Rust 无稳定 ABI，跨版本加载是长期维护灾难，收益（省几 MB）远不抵风险。
- **备选三：现状单胖二进制**。弃选：维护者明确否决。
- **代价：多二进制的版本漂移。** 由 §2 的双版本握手承担；`tokly doctor` 列出各形态版本与兼容区间。
- **代价：`tokly install` 需要一个更新通道**（release 索引 + 校验）。接受：它同时服务核心自更新，本就要建；下载校验用 cargo-dist 已生成的 checksum 清单，不自造。
- **代价：桌面内嵌核心导致双份**。接受：这是"非命令行用户双击即用"的必要交换，且单 owner 锁已保证数据面安全。

## 后果

- [架构](../架构.md) 增「形态分发」节；crate 图明确 `tokly-tui` / `tokly-web` 不被核心依赖，反向亦然；
- 工作区新增 `crates/tokly-web`（现有 `tokly-server` 的服务面迁入并嵌入前端产物）；
- [路线图](../路线图.md) M4 增 `tokly install` 与形态产物矩阵；M1 只需保证 crate 边界正确，不实现安装器；
- CI 产物矩阵按 形态 × 平台 展开；`cargo xtask ci` 增「核心不得依赖 ratatui / 前端资源」的边界断言；
- [ADR-0014](0014-诊断与格式演进.md) 的 doctor 输出增：已安装形态清单、各自版本、兼容性判定。
