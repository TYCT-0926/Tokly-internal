# ADR-0010: 配置子系统

- 状态：accepted
- 日期：2026-08-03

## 背景

多处已定的机制依赖"用户可配置"，但配置本身从未被规格化：

| 依赖方 | 需要的配置 |
|---|---|
| [风险登记](../风险登记.md) R3 | 同源多通道的**唯一权威通道**选择 |
| [ADR-0008](0008-配额窗口.md) | 配额窗口规则覆盖、用户显式容量 |
| [ADR-0011](0011-存储生命周期.md) | 各层保留期 |
| [ADR-0002](0002-数据架构.md) | 定价用户覆盖文件路径、远程刷新开关 |
| [数据库-schema](../数据库-schema.md) | `source_instances.machine`——"安装期生成并持久化"，持久化到哪从未定义 |
| [ADR-0005](0005-主题架构.md) · [ADR-0007](0007-国际化.md) | 主题、语言、时区 |

没有格式、位置、优先级、校验与迁移规则，上述机制全部无法落地。

## 决策

### 位置与格式

- 配置文件：`<config_dir>/tokly/config.toml`（Linux `~/.config`、macOS `~/Library/Application Support`、Windows `%APPDATA%`）
- 机器标识：`<data_dir>/tokly/machine`，首次启动生成随机 UUIDv4 并持久化。**不含任何硬件指纹**——它只需在本机稳定，不需要能识别本机。
- 格式 **TOML**：可注释、可手写、Rust 生态成熟。配置是人写的，JSON 不合适。

### 优先级

内置默认 < 配置文件 < 环境变量（`TOKLY_*`）< CLI 参数。高优先级只覆盖显式给出的键，不整体替换段落。

### 内容骨架

```toml
version = 1

[general]
locale = "system"           # system | zh-CN | en
timezone = "system"         # system | IANA 时区名；锁定后历史日界不再随系统漂移
theme = "amber"
theme_mode = "system"       # system | dark | light
update_check = true         # 检查更新开关（ADR-0013：检查默认开、安装必确认）
log_level = "warn"          # 日志等级（ADR-0014）；TOKLY_LOG 按优先级链覆盖本键

[retention]                 # 见 ADR-0011，约束 observations_days <= events_days
observations_days = 90
events_days = 180

[server]
port = 0                    # 0 = 随机可用端口

[pricing]
remote_refresh = true
override_path = ""          # 用户 pricing.json；空 = 不启用

[sources.claude-code]
enabled = true
data_root = ""              # 空 = 平台默认路径
authoritative_channel = ""  # 多通道源必填，见 R3

[quota.claude]
rule_version_override = ""
capacity = 0                # >0 时才生成 used_pct，provenance = user-configured
```

> 2026-08-03 增补（阶段三A 配置面核查）：`update_check` 与 `log_level` 两键此前有消费者无骨架，补入；API 源授权凭据**不进 config**（钥匙串承载，ADR-0003），其配置面（如启用开关）推迟至 M6 Copilot 落地时增补。

### 校验与失败策略

启动即全量校验：未知键、类型错误、越界值、互斥项冲突一律**拒绝启动**，错误指到键路径与行号。与全局 fail-visible 一致——静默回退默认值会让用户以为配置生效了。

`tokly config check` 单独跑校验；`tokly config get|set` 提供不手改文件的通路，`set` 后重新校验并保留注释与键序。

### 迁移

`version` 单调递增。升级时按版本迁移并把原文件备份为 `config.toml.bak.<旧版本>`；迁移失败不覆盖原文件。

### 与 daemon 的关系

配置由 daemon 启动时读取并持有。运行中修改需重启 daemon 生效，唯一例外是 `[general]` 的展示类项（主题、语言、时区）——它们经 IPC/SSE 热更新，不重启。

## 为什么现在做

配置不是一项功能，是**已定机制的落地面**：R3 的权威通道、ADR-0008 的用户容量、ADR-0011 的保留期、定价覆盖，四条对冲目前全部悬空。更硬的是 `source_instances.machine`——它是 schema 已经引用、事件身份直接依赖、却从未定义存放位置的字段，属 M0.5 冻结门范围（身份构成一旦入库不可逆）。

推迟的具体代价：M1 摄取会先落一批 `machine` 未定义或每次临时生成的实例 ID，事件身份被污染，且因为跨实例不去重，污染无法靠重扫消除。

## 代价与备选

- **代价**：多一个配置文件与校验路径，增加启动期失败面。取舍是明确的——拒绝启动优于静默回退：后者会让用户以为权威通道已生效，而多通道双计数是静默的，错误会一直累积到有人核对账单才发现。
- **备选一：全部走 CLI 参数与环境变量。** 弃选理由：权威通道、配额容量这类"一次设定长期生效"的项不适合放命令行，且桌面端根本没有命令行入口。
- **备选二：配置存进数据库。** 弃选理由：端口与数据目录恰恰要在 daemon 起来之前读到，配置进库形成循环依赖；且会让配置与数据的备份、迁移耦合。
- 骨架刻意保持最小：**每一项都对应一条已有决策，没有为将来预留的项。** 新增配置项必须先改本 ADR——这条纪律比骨架本身重要，配置面是最容易长成垃圾场的地方。

- 新增 CLI 子命令 `tokly config check|get|set`。
- `machine` 文件与数据库同目录：备份数据目录即备份身份；跨机器复制会得到不同 `machine`，因而不互相去重——与 [ADR-0002](0002-数据架构.md) 事件身份模型一致。
- 配置项集合属活文档，新增或变更与本 ADR 同 PR 更新。
- 设置界面的规格见[组件规格](../design/组件规格.md)，它是本配置面的 UI 投影，不引入配置面之外的项。
